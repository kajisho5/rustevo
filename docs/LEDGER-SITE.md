## 1. 目的

設計メモの成功の定義「公開台帳がある」「毎週、台帳が伸びるのが外から見える」を満たすページ。
見る人は 2 種類。

- 初めて来た人: 30 秒で「何が残っていて、なぜ信用できるか」が分かる。
- 毎週見に来る人: いちばん上で、新しく増えた世代と合否が分かる。

## 2. 要件

1. 台帳の一覧: 全世代を新しい順に。番号、合否、意図、記録の結果（一致・相違・引退の本数）、ハッシュの先頭。
2. 世代の詳細: 意図、判定と理由、**宣言と実測の対照表**、記録ごとの結果（ステップごとの値の違い）、plan の差分、画面の参考表示、ハッシュ、確かめ方のコマンド。
3. 不合格の世代を隠さない。一覧では本線から外れた枝として見せる。
4. 「検証済み」の表示は、実際に検証が通ったときだけ出す（ページを作る処理の中で `verify` を実行し、失敗したらページを作らない）。
5. スマホで読める。1 列。横スクロールなし。
6. 英語と日本語の 2 種類を出す（画面の文言のみ。意図の文はエージェントが書いたまま）。
7. JavaScript なしで全部読める。折りたたみは HTML の標準機能（`details`）を使う。

やらないこと: 検索、絞り込み、ログイン、コメント、解析タグ。

## 3. 技術選定

| 候補 | 動作の軽さ | 配布サイズ | 作りやすさ | 対応環境 | 将来性 | AI での書きやすさ |
|---|---|---|---|---|---|---|
| A. `evo site`（Rust の道具が HTML を直接書き出す） | ◎ JavaScript なし | ◎ HTML と CSS のみ | ○ 文字列の組み立て | ◎ どのブラウザでも | ○ 道具と一緒に進化 | ○ |
| B. Astro（台帳の JSON を読んで生成） | ◎ | ○ | ◎ 部品化しやすい | ◎ | ◎ | ◎ |
| C. 単一 HTML ＋ JavaScript（開いたときに台帳を読む） | ○ | ◎ | ◎ | △ JavaScript 必須 | △ | ◎ |

**おすすめ: A**。理由は 3 つ。

- ページは証跡の出力そのもの。検証する道具と同じものが書き出せば、「検証が通ったものだけが載る」を 1 か所で保証できる。
- 値の違いをステップごとに出すには、再演をやり直す必要がある。それができるのは Rust の中核部分だけ。B と C は中間の JSON を別に作ることになり、二重管理になる。
- Node が要らない。リポの道具が Rust だけで済む。

目安（表示中心のサイトは Astro）から外れるので明記する。部品が増えて文字列の組み立てがつらくなったら B に移る。

## 5. 部品

| 部品 | 使う場所 | 役割 |
|---|---|---|
| 上の帯 | 両方 | 名前（詳細では「台帳」へ戻る）、言語の切り替え |
| 検証済みの札 | 一覧 | 世代数、確認した CPU、コミット、日付、確かめ方 |
| 数の枠 | 一覧 | 試み・合格・不合格 |
| 世代の行 | 一覧 | 合格は本線上の緑の丸。不合格は赤い枠つきの行 |
| 合否の札 | 両方 | 合格（緑）、不合格（赤）、相違（黄）、変更（灰） |
| 判定の箱 | 詳細 | 理由を 1 文で |
| 対照表 | 詳細 | 種類・名前・宣言・実測。宣言外の行を赤に |
| 画面の参考表示 | 詳細 | 親とこの世代を横に並べる。違う要素に色 |
| 記録の折りたたみ | 詳細 | 開くとステップごとの値（親 → この世代） |
| ハッシュの表 | 詳細 | 世代・親・plan・ロジック |
| コマンドの箱 | 詳細 | 確かめ方。コピーのボタンだけ JavaScript を使う（なくても読める） |

## 6. 状態管理

なし。すべて静的な HTML。開閉は `details`、言語はページを分ける。

## 7. データ

入力は既にあるファイルだけ。新しい保存形式は作らない。

- `ledger.jsonl`、各世代の `gen.json` `change.json` `verdict.json` `carry.json` `plan.diff.json`
- ステップごとの値の違いと画面の木は、`evo site` が再演をやり直して求める（`carry.json` には最初に違ったステップの番号しかない）。そのために中核部分に「違いの詳細を返す」関数を 1 つ足す。
