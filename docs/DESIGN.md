## 1. 目的・成功の定義・差別化

### 1.1 目的

rustevo は、**エージェントがアプリを書き換え続けても、何が変わって何が変わらなかったかを第三者が再演で確かめられる** Rust アプリフレームワーク。

納品の単位を「ビルド」ではなく「**世代**」にする。世代とは次の 3 点の組。

1. ソース（`.evo` と Rust）
2. plan（`.evo` を事前コンパイルしたもの）
3. 証跡（操作の記録、前の世代との比較結果、判定）

### 1.2 守る約束（不変条件）

| 番号 | 約束 | 中身 |
|---|---|---|
| 約束1 | 決定性 | 同じ plan と同じ記録からは、どの機械でも同じ状態・同じ画面の木が 1 ビットも違わず再現される |
| 約束2 | 完全記録 | アプリの外から入るもの（操作、時刻、通信や保存の結果、乱数）は、すべて記録を通る。記録を通らない入口を作らない |
| 約束3 | 世代の連鎖 | 各世代は親世代のハッシュを持つ。途中を書き換えると以降の検証がすべて失敗する |
| 約束4 | 宣言と実測の一致 | 世代を作るとき「何を変えるか」を先に宣言する。実際に変わった範囲が宣言からはみ出たら、その世代は不合格 |

約束4 が製品の芯。「エージェントは A を変えたと言っている。証跡でも A しか変わっていない」を機械的に示す。

### 1.3 成功の定義

採用数では測らない。次の 3 つで測る。

1. **公開台帳がある**: デモアプリの全世代（意図、plan の差分、判定、画面）が Web で誰でも見られる。
2. **第三者が検証できる**: リポジトリを取ってきて 1 コマンド（`evo verify`）で、全世代の検証が通る。作者を信用する必要がない。
3. **毎週 1 世代以上、台帳が伸びる**: 進化が外から見える。不合格になった試みも台帳に残す。

### 1.4 差別化

一言で: **Exact は「速く、どこでも、エージェントが書ける」。rustevo は「書き換え続けても、証跡で確かめられる」。**

速さ・対応 OS の数・書きやすさでは競わない。これらを README の見出しに出さない。

## 2. 言語（`.evo`）

### 2.1 方針

- 宣言専用。ロジックは Rust。この線は変えない。
- 構文の上限は **14**。足すなら消す。
- 追加の判断基準を 1 つ足す: **「証跡に効くか」**。証跡に効かない構文は入れない。

### 2.2 14 構文（案）

注意: 以前の 14 構文の一覧は手元にない（未確認）。下は一から組み直した案。

| 区分 | 構文 | 役割 |
|---|---|---|
| 宣言 | `app` | アプリの根。名前と最初の画面 |
| 宣言 | `use` | 別の `.evo` ファイルを読み込む |
| 宣言 | `state` | 状態の項目。型と初期値 |
| 宣言 | `derive` | 派生値。状態から計算する値（2.3） |
| 宣言 | `invariant` | 常に成り立つべき条件。**毎ステップ検査して証跡に残す** |
| 宣言 | `every` | 時計の購読。「1 秒ごとにこのアクション」を宣言する |
| 宣言 | `view` | 画面の部品。引数を取れる |
| 宣言 | `style` | 名前つきの見た目の組 |
| 画面内 | 要素 | `種類 #id { 属性; 子 }`。部品の呼び出しも同じ形 |
| 画面内 | `if` | 条件で出し分け |
| 画面内 | `for` | キーつきの繰り返し |
| 画面内 | `on` | イベントの受け口 |
| 受け口内 | `set` | 状態への直接代入 |
| 受け口内 | `do` | Rust アクションの呼び出し |

以前の設計から変えた点（推測を含む。旧一覧が手元にないため）:

- 足した: `invariant`、`every`。どちらも証跡のため。
- 持たない: 画面遷移専用の構文。今どの画面かは普通の `state` にして `if` で出し分ける。遷移も状態の変化として記録に残る。
- 持たない: テスト専用の構文。テストは「記録」と「持ち越し再演」（3.5）が担う。

### 2.3 型と id の決まり

- 型は `state` の一部として書く。使えるのは 真偽 / 整数（64 ビット固定）/ 文字列 / 列挙 / リスト / レコード。
- **小数は状態に持たせない**。機械によって結果がずれる原因になる。時間は秒やミリ秒の整数で持つ。
- 状態の形は `.evo` が正。Rust 側の型は `.evo` から自動生成する。二重管理しない。
- **操作できる要素と、文字を表示する要素には `#id` を必須にする**。コンパイラが強制する。id は世代をまたいで要素を対応づける鍵になる。

### 2.4 派生値の扱い（提案）

3 案を比べた。

| 案 | 中身 | 証跡への効き | 言語の大きさ | 判断 |
|---|---|---|---|---|
| A | 言語内の `derive`。副作用なしの式だけ | 高い。式が plan に入るので差分が取れる | 構文 1 つ | **採用** |
| B | Rust の関数で派生値を計算 | 低い。中身が plan から見えない。決定性も保証しにくい | 増えない | v0.1 では不採用 |
| C | 派生値を持たず、全部アクションが状態に書く | 中。状態が膨らみ、書き忘れで食い違う | 減る | 不採用 |

A の決まり:

1. `derive` の式は、状態と他の `derive` だけを読める。繰り返し・再帰・Rust 呼び出しは書けない。必ず終わる。
2. 依存が輪になっていたらコンパイルエラー。
3. 使える関数は言語が決めた閉じた一覧だけ（件数、合計、含むか、時間の書式化など）。関数は語彙であって構文ではない。足すときも一覧に 1 行足すだけ。
4. **派生値は保存しない。記録にも「入力」としては入れない**。状態から毎回計算できるものを真実として二重に持たない。
5. ただし**各ステップで派生値のハッシュは証跡に残す**。式を変えた世代で「状態は同じ、派生値だけ違う」と見分けるため。
6. 式で書けない複雑な派生は、アクションが計算して状態に書く。その場合それは派生値ではなく状態として扱う。

### 2.5 例（案）

```
app Pomodoro

state phase: idle | focus | rest = idle
state remaining: int = 1500
state done: int = 0

derive label = mmss(remaining)
derive running = phase != idle

invariant remaining >= 0
invariant done >= 0

every 1s when running do tick

view Main {
  column #root {
    text #timer { label }
    if running {
      button #stop { "Stop"; on tap set phase = idle }
    } else {
      button #start { "Start"; on tap do start }
    }
    text #count { "done: {done}" }
  }
}
```

## 3. plan・状態機械・ドライバ・証跡

### 3.1 plan

plan は `.evo` をコンパイルした結果。中身は次の 7 つ。

1. 状態の形（項目と型）
2. 派生値の式と依存関係
3. 画面の木のひな形（id つき）
4. 受け口の表（どの id のどのイベントで何をするか）
5. 時計の購読の一覧
6. 不変条件の一覧
7. 見た目の表

決まり:

- 並び順まで固定した形で書き出す。同じ `.evo` からは必ず同じバイト列になる。
- そのバイト列の SHA-256 を **plan のハッシュ**とする。
- 2 つの plan を比べて「増えた id / 消えた id / 変わった受け口 / 変わった式 / 変わった状態の形」を出す **plan 差分**を機械で作る。レビューする人はソースの差分より先にこれを読む。

### 3.2 状態機械

アプリ全体を 1 つの関数として扱う。

```
ステップ(状態, できごと) → (新しい状態, 外への依頼の列)
画面の木 = 描く(plan, 状態, 派生値)
```

できごとは 4 種類で閉じる。

| できごと | 中身 |
|---|---|
| `init` | 開始。plan のハッシュ、ロジックのハッシュ、乱数の種 |
| `input` | 操作。どの id に何をしたか |
| `tick` | 時計を進める。進めた先の時刻 |
| `result` | 外への依頼の結果が返ってきた |

Rust アクションの形（案）:

```rust
pub fn tick(s: &State) -> Outcome   // Outcome = 状態の変更の列 + 外への依頼の列
```

- アクションは状態を読んで、変更と依頼を**データとして返すだけ**。自分では通信も保存もしない。
- 外への依頼（通信、保存、乱数）はランタイムが実行し、結果を `result` として記録に書く。
- 再演のときは依頼を実行しない。記録にある結果をそのまま返す。だからネットワークなしで再演できる。

決定性の守り方（v0.1）:

1. 現在時刻や乱数を直接読む関数を、検査ツール（clippy の禁止一覧）で禁止する。
2. 検証モードでは各アクションを 2 回実行し、結果が違えば失敗にする。
3. 状態の入れ物は順序が決まるものだけ使う。

これは「規約＋検査」であって、完全な封じ込めではない（7 章の未決 1）。

### 3.3 記録（ジャーナル）

- 1 行 1 できごとのテキスト（JSON Lines）。人が読めて差分が取れる。
- 追記のみ。各行は直前の行のハッシュを持つ。

1 行の中身（案）:

```json
{"seq":12,"t":3000,"ev":{"tick":3000},
 "changed":{"remaining":1497},
 "state":"9f2c…","derive":"41aa…","tree":"c07e…",
 "requests":[],"invariants":"ok","prev":"5b1d…"}
```

ハッシュは 3 層で取る。変更の種類が層で分かる。

| 変えたもの | 状態 | 派生値 | 画面の木 |
|---|---|---|---|
| 画面の組み替えだけ | 同じ | 同じ | 違う |
| 派生値の式 | 同じ | 違う | 違う（表示に出る場合） |
| アクションのロジック | 違う | 違う | 違う |
| 内部の整理だけ | 同じ | 同じ | 同じ |

**画面の木のハッシュは論理的な木（id、種類、属性、文字）で取る。座標や画素では取らない**。レイアウト計算や描画は機械で微妙にずれうるため、約束1 の対象から外す。スクリーンショットは「参考の証跡」として添えるが、合否には使わない。

### 3.4 実行の 3 モード

| モード | 使う場面 | 動き |
|---|---|---|
| 記録 | エージェントが操作して確かめるとき | 実際に依頼を実行し、すべて記録する |
| 厳密再演 | 同じ世代の検証 | 同じ plan で記録を流す。1 行でもハッシュが違えば、そのステップで失敗 |
| 持ち越し再演 | 世代をまたぐ検証 | 親世代の記録を新しい plan に流し、違いを分類する（3.5） |

### 3.5 持ち越し再演と世代の判定

進化の証跡の中心。

手順:

1. エージェントは変更の前に**変更宣言**を書く。「どの状態の項目、どの id が変わるはずか」と理由。
2. 変更する。
3. 親世代の記録から、外から来たできごと（`input` / `tick` / `result`）だけを取り出し、新しい plan に最初から流す。
4. ステップごとに比べる。状態は両方にある項目を名前で、画面の木は id で対応づける。
5. 記録ごとに結果を 3 つに分ける。

| 結果 | 意味 |
|---|---|
| 一致 | 最後まで同じ |
| 相違 | どのステップで、どの項目・どの id が違ったか |
| 適用不能 | 操作先の id が消えた、記録にない依頼が出た、など。理由つき |

6. 判定する。

| 判定 | 条件 |
|---|---|
| 合格 | 見つかった相違と適用不能が、すべて変更宣言の範囲内。不変条件もすべて成立 |
| 不合格 | 宣言していない項目や id が変わった。または不変条件が破れた |
| 注意つき合格 | 宣言したのに実際には変わっていない箇所がある |

7. 合格したら、新しい世代で記録を取り直して封をする。適用不能になった記録は、理由を残して引退させる。

最初から流すので、v0.1 では状態の移行処理はいらない（保存済みデータの移行は 7 章の未決 3）。

### 3.6 世代と台帳

世代 1 つ = フォルダ 1 つ（案）:

```
generations/0007/
  gen.json        親のハッシュ、ソースのハッシュ、plan のハッシュ、作った主体
  change.toml     変更宣言
  plan.bin        plan
  plan.diff.json  親との plan 差分
  journals/       この世代で取った記録
  carry.json      持ち越し再演の結果
  verdict.json    判定
  shots/          参考のスクリーンショット
```

- フレームワークとデモアプリは同じリポジトリに置く。世代 1 つがコミット 1 つに対応する。
- ソースのハッシュは `generations/` を除いた中身で取る。
- Rust のツールのバージョンと依存の固定ファイルをコミットする。古い世代も同じ条件で作り直せる。
- **不合格になった試みも台帳に残す**。「止めた記録」が、仕組みが働いている証拠になる。
- 台帳（`ledger.jsonl`）は世代ごとに 1 行。ここから静的な Web ページを作って公開する。

### 3.7 ドライバ（8 操作）

**ドライバを唯一の入口にする**。ドライバを通らない操作は存在しないので、入力はすべて記録に残る（約束2）。

| 区分 | 操作 | 中身 | 記録に残るか |
|---|---|---|---|
| 見る | `tree` | 画面の木 | 残らない |
| 見る | `state` | 状態と派生値 | 残らない |
| 見る | `journal` | 記録の読み出し。ログも兼ねる | 残らない |
| 見る | `screenshot` | 画像（参考） | 残らない |
| 入れる | `tap` | id を押す | 残る |
| 入れる | `type` | id に文字を入れる | 残る |
| 入れる | `clock` | 時計を進める | 残る |
| 入れる | `respond` | 外への依頼に結果を返す（通信の代役） | 残る |

以前の 8 操作から変えた点:

- 消した: `logs`（`journal` に統合）、`perf`（計測値は毎回変わるので証跡にならない。速さは競わない）。
- 足した: `journal`、`respond`。

コマンド（ドライバとは別）:

| コマンド | 中身 |
|---|---|
| `evo build` | `.evo` → plan。エラーは機械が読める形で返す |
| `evo run` | 記録モードで起動 |
| `evo replay` | 厳密再演 |
| `evo carry` | 持ち越し再演 |
| `evo seal` | 判定して世代に封をする |
| `evo verify` | 台帳全体を検証。連鎖の確認、全世代の厳密再演、判定のやり直し |

## 5. Exact との差別化の評価

### 5.1 軸ごとの評価

| 軸 | Exact（事実） | rustevo | 開発者は気にするか（推測） |
|---|---|---|---|
| 速さ | 120fps、ほぼ即起動をうたう | 競わない | 強く気にする。ここは負け |
| 対応 OS | 4 つ＋初期段階 2 つ | ヘッドレスのみ | 強く気にする。ここは負け |
| 小さい言語 | 意図的に小さい。数は非公表 | 14 で固定 | ほぼ気にしない。差にならない |
| Rust でロジック | Rust か TypeScript | Rust のみ | 差にならない |
| エージェント操作 | 10 操作、全ホスト共通 | 8 操作 | 差にならない |
| 時計の所有 | エージェント | ランタイム（ドライバ経由） | 差にならない |
| 操作の記録と再演 | README に記述なし | 中心機能 | 一部の人だけ気にする |
| 世代間の比較と判定 | README に記述なし（テストファイルで確認する方式） | 中心機能 | 一部の人だけ気にする |
| 公開の台帳 | 記述なし | 中心機能 | 一部の人だけ気にする |

### 5.2 率直な評価

1. **以前の 4 つの差別化は成立していない**（事実に基づく）。依頼資料の見立てどおり。
2. **新しい軸は、Exact の README に書かれていない領域ではある**（事実）。ただし「実装に存在しない」とまでは確認できていない（未確認）。
3. **一般のアプリ開発者の多くは、この差で選ばない**（推測）。フレームワークは、動く OS、速さ、部品の多さで選ばれる。「後から監査できる」は選ぶ理由の上位に来ない。
4. **気にする人はいる**（推測）。
   - エージェントに何度も書き換えさせ、差分を全部は読めない人。「壊れていない」を読まずに確かめたい。
   - 変更の説明責任がある現場。
   - エージェントの作業を研究・評価する人。
5. **堀は薄い**（推測）。Exact は土台を持っているので、同じ機能を足せる。先に形にして、台帳という実績を積むことだけが優位になる。
6. **それでも成功の定義には合っている**。成功の定義は採用数ではなく「実演の公開」と「週次の進化が見えること」。台帳はそのまま「見える進化」になる。市場で Exact に勝つ差ではないが、**この計画の目的を満たす差**ではある。

### 5.3 効率の指摘

独自の部分（記録、持ち越し再演、判定、台帳）は、独自の言語や描画がなくても成り立つ。**いちばん安く同じ差別化に届く道は、Exact の上に証跡の層だけを作ること**。Exact は Rust のロジックとヘッドレスの Linux ホストを持っている。

今それを勧めない理由:

- 事実: Exact は毎日変わり、互換性を保証しないと明言している。上に載せた層は頻繁に壊れる。
- 推測: 約束1 と約束2 は、ステップ関数と外への依頼の境界を自分で握っていないと保証できない。外側からは守り切れない。

対策として、次を設計に入れる。

- **証跡の形式（記録、世代、台帳）を `.evo` から独立した仕様として書く**。将来、他のフレームワークに差し替えられる余地を残す。
- 描画・速さ・対応 OS に時間を使わない。使った分だけ Exact との不利な比較が増える。

### 5.4 結論

- 「フレームワークとして Exact と競う」: 勝てない。やらない。
- 「エージェントが進化させるアプリの、証跡つきの実演」: 成立する。対象は狭いが、成功の定義に直結する。
- この方向で進めてよい。ただし README では Exact の強みを認め、用途で住み分ける書き方にする。

## 6. README の文面案

### 6.1 一文

推奨:

> **rustevo — the Rust framework for apps that agents evolve, with a replayable record of every change.**

依頼資料の案（"The Rust framework for apps that evolve — and keep the evidence."）は響きがよいが、"evolve" の主語と "evidence" の中身が伝わりにくい。「誰が」「何が残るか」を入れた。

別案:

- 短さ優先: **Apps that evolve — and keep the evidence.**
- 検証を前面に: **Every change replayable. Every generation verifiable.**

日本語:

> **rustevo — エージェントが進化させるアプリのための Rust フレームワーク。すべての変更が、再演できる記録として残る。**

### 6.2 Differentiation 節（英語）

```markdown
## Differentiation

rustevo is not trying to be the fastest framework or to run on the most
platforms. If that is what you need, use [Exact](https://github.com/expo/exact).
It is faster, runs on more hosts, and lets you write logic in TypeScript.

rustevo answers a different question: **after an agent has changed your app
fifty times, how do you know what actually changed?**

- **Every run is a record.** Input, time, and every result from the outside
  world go through one journal. The same journal on the same build gives the
  same state and the same UI tree, bit for bit, on any machine.
- **Every change is a generation.** A generation is source, compiled plan,
  and evidence, linked to its parent by hash. Change one byte in the past
  and verification fails.
- **Changes are declared, then measured.** Before a change, the agent states
  what will differ. The previous generation's journals are replayed on the
  new build. Anything that differs outside the declaration fails the
  generation.
- **The ledger is public.** Every generation of the demo app, including the
  rejected ones, is published. Clone the repository, run `evo verify`, and
  check it yourself.

What rustevo does not do: Android, Windows, device APIs, a visual editor,
a JavaScript logic layer, or compatibility promises before 1.0.
```

### 6.3 Differentiation 節（日本語）

```markdown
## 他との違い

rustevo は、いちばん速いフレームワークも、いちばん多くの OS で動く
フレームワークも目指していません。それが必要なら
[Exact](https://github.com/expo/exact) を使ってください。Exact のほうが速く、
多くの環境で動き、TypeScript でもロジックを書けます。

rustevo が答えるのは別の問いです。**エージェントがアプリを 50 回書き換えた
あと、実際に何が変わったのかを、どうやって確かめるか。**

- **すべての実行が記録になる。** 操作、時刻、外から返ってきた結果は、
  すべて 1 本の記録を通ります。同じ記録を同じビルドに流せば、どの機械でも
  同じ状態と同じ画面の木が再現されます。
- **すべての変更が世代になる。** 世代は、ソース・plan・証跡の組です。
  親の世代とハッシュでつながっていて、過去を 1 バイト書き換えると検証が
  失敗します。
- **変更は先に宣言し、あとで実測する。** 変更の前に、何が変わるかを
  エージェントが宣言します。前の世代の記録を新しいビルドで再演し、宣言の
  外で違いが出たら、その世代は不合格です。
- **台帳は公開されている。** デモアプリの全世代を、不合格になったものも
  含めて公開しています。リポジトリを取得して `evo verify` を実行すれば、
  自分で確かめられます。

やらないこと: Android、Windows、デバイス機能、ビジュアルエディタ、
JavaScript のロジック層、1.0 前の互換性の約束。
```

## 7. 未確認・未決

未確認（読めていないもの）:

- Exact は README と発表の投稿だけを確認した。**ソースコードと `docs/` は読んでいない**。「記録・再演がない」は README に記述がないという意味で、実装に存在しないことは確認していない。
- 以前の rustevo の設計（14 構文の一覧、plan の形式、ドライバの仕様）は依頼資料の要約しか見ていない。
- 借り物のライブラリの最新バージョン、vello の CPU 描画がヘッドレスの Linux で使えるかは確認していない。使えない場合は別の描画ライブラリに替える。
- GitHub の自動実行で ARM の Linux が無料で使えるかは確認していない（完2 の前提）。

未決（実装前に決める）:

1. **ロジックの封じ込め**: v0.1 は「禁止一覧＋2 回実行」。本命は Rust ロジックを WebAssembly（どこでも同じに動く中間形式）にして世代に同梱する方式。古い世代をビルドし直さずに再演でき、時刻や通信を物理的に読めなくなる。v0.2 の最有力候補。
2. **持ち越し再演の細かさ**: 変更宣言を項目と id の単位にするか、記録の単位まで書かせるか。まず項目と id の単位で始める。
3. **保存済みデータの移行**: 状態の形が変わったとき、利用者の端末に残ったデータをどう扱うか。v0.1 では扱わない。
4. **ハッシュの方式**: SHA-256 を仮置き。どの環境でも標準の道具で確かめられることを優先した。
